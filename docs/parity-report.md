# Esquie feature parity and verification

**Status: substantial working local implementation; not full product or visual parity.**

Application code, tests, configuration examples and documentation live in the target repository, not merely session artifacts. The initial untracked-file visibility problem was corrected with local commits. This report accompanies an **explicitly incomplete interim public source baseline**, not a feature-complete release or approval to distribute desktop artifacts. Owner-reviewed local outcome import, the workshop-import parser correction, local task-board moves/context search, a standalone selected-text adapter, owner/source-bound reply previews, an explicit desktop workspace environment override, recorded-document backups, validated task-evidence provenance and reviewed approval/recovery boundary guards are included in public main. These are not evidence of a complete desktop release; the selected-text adapter has no app content UI or production sign-in, and its default Windows downloader remains unavailable. The operational warnings below remain limitations of the published code.

## Current operational warnings

The following limitations are present in the published code; this documentation does not fix them:

- Legacy invalid timezone state can make worker ticks fail. Incomplete or malformed quiet-hour state may be treated as no quiet window. Keep the worker paused; if pausing is rejected, quit the host and do not resume scheduled work until the saved timezone and both quiet-hour values are corrected.
- Mixed successful and denied source reads can show misleading availability. Stored source previews are historical and do not establish current source selection or consent. Reads already in flight are not cancelled by pause, quiet hours, or shutdown and may retain results afterward. Keep optional/injected connectors disconnected and do not act on historical source previews.
- Resubmitting after an uncertain response with a new request ID can duplicate work. Demo Retry does not require fresh fake-only confirmation; inspect Activity and output, and do not retry demos.

Microsoft 365 and Copilot remain disconnected by default. The existing workshop-import parser correction is already on public main.

## Safe connection wiring

`startServer({dataDir,port})` remains compatible with the desktop wrapper and returns an idempotent `close()` handle. A trusted host may supply `microsoft365Options: {tokenProvider,transport?}`; the factory and tokens never enter browser configuration, SQLite or job results. See [safe-source-connectors.md](safe-source-connectors.md) for precise scopes, source formats, error codes, opaque-ID limits and authentication prerequisites.

The UI/API separately accepts owner identity expectations, exact source selections, source consent and unsent-draft consent. Only successful authenticated verification saves the nonsecret selections. Restart does not silently reconnect. `/me` + `User.Read` verifies only the owner: source availability stays `access-unverified` until a successful bounded read, is timestamped, and resets on failures/disconnect/reconnect/identity changes. A User.Read-only synthetic regression proves it cannot appear as source access.

No trustworthy production token provider is available in this environment. Device-code/OIDC is not invented or enabled from entered IDs; no real sign-in was attempted. Package-policy/authentication-library and app-registration prerequisites remain genuine blockers, not fake successful connections.

The standalone selected-text operation is not enabled by the app's metadata source consent. It needs a separately owner-triggered, CSRF-protected exact-host action and an inert local text display; neither is implemented. Its built-in transport requires explicit permitted direct egress and rejects configured proxy/TLS-bypass settings; on Windows it always returns unavailable before DNS because system/enterprise proxy policy cannot be established. It never clears settings or substitutes another route. Synthetic download tests do not establish live source availability, and selected content is not sent to workers, task discovery, an assistant or cloud storage.

The Azure CLI assessment does not enable a provider: documented token output does not establish the authenticated user object or actual delegated grants, and `Bearer`/requested scopes are not proof of delegated authorization. Same-token `/me` alone does not establish the tenant assertion or granted scopes; a separate active-account lookup can race. Graph access tokens must be treated as opaque, not decoded as verified JWTs to fill the missing metadata. Production sign-in therefore remains disconnected; no local CLI account/cache/token or live Graph operation was inspected or used. See the [detailed assessment](safe-source-connectors.md#azure-cli-alternative).

The assistant production bridge remains disconnected. The isolated audit of official CLI 1.0.109 plus extracted SDK observed a configured synthetic MCP process starting despite empty tools/MCP options and disabled discovery, plus managed-settings/team-customizations fetch attempts in a loopback-only fake-identity test. No real credentials/model/service access occurred. This is an observed process/network isolation failure, not merely a version mismatch; empty reported tool inventory is insufficient. The synthetic factory is confined to tests, never imported by the host. See [assistant-bridge-integration.md](assistant-bridge-integration.md) for exact evidence and production-provider requirements.

## Owner launch authorization

Every sensitive API requires `X-Esquie-Access` with a per-start 256-bit capability; `/api/health` is intentionally minimal and unauthenticated. The capability is not included in state, logs, query strings or public shell assets. A protected `esquie-launch.html` supplies `http://127.0.0.1:<port>/#access=<43-character base64url token>`; the trusted desktop host receives the same `launchUrl` in memory. The renderer immediately replaces the fragment and stores the capability only in per-window, origin-specific session storage (or warns about memory-only operation).

Origin/CSRF and sensitive cross-site checks still apply independently. Only a top-level navigation to the public root shell is allowed cross-site so a local launch file can open it. Normal close stops the host and removes only its matching private launcher. Any existing workspace lock blocks startup without automatic stale-lock deletion; after a crash, the lock requires independent ownership/process review before manual action. Only after exclusive workspace access is established can a recognized crash launcher be replaced; old capabilities are rejected. Unrelated or modified launcher files are preserved, with an explicit failure rather than silent replacement. This does not isolate malicious same-user processes, administrators or compromised browser profiles.

## Storage protection and output containment

The web host uses `%USERPROFILE%\.esquie-local`; desktop uses `%LOCALAPPDATA%\EsquieLocal\Workspace`. These are separate default workspaces, not shared automatic state. An ordinary browser may open the already-running desktop host's protected launcher without starting another backend. To start standalone against desktop state, explicitly Quit desktop first, set `$env:ESQUIE_DATA_DIR = Join-Path $env:LOCALAPPDATA 'EsquieLocal\Workspace'`, then run `npm start`; stop standalone before opening desktop again. Desktop also honors an explicit `ESQUIE_DATA_DIR` in its launching environment, below an injected `dataDir` and above its unchanged default. This can select a separately adopted or paused recovered recreation directory after its owner has quit; it never merges, relocates or automatically migrates state. Backend ownership/privacy/lock guards remain mandatory. Graphical selection and automatic attachment/handoff remain missing parity, not permission to bypass a lock; shortcuts/startup may not inherit a terminal-only override.

Optional `ESQUIE_DATA_DIR` must be outside the repository and known/configured sync roots. `ESQUIE_SYNC_ROOTS` must be a JSON array of absolute paths; malformed values fail before state is created.

Windows startup creates restrictive current-user/SYSTEM/Administrators ACLs only on a newly created empty app directory. Existing app directories and state/document files are inspected without replacing their permissions. Broad grants, unverified owners, redirected storage, unsafe ancestor replacement rights or unavailable inspection block startup. Actual Windows tests verify both new storage/restart and rejection without ACL changes. PowerShell uses the system executable/module path and an allowlisted environment, not ambient provider configuration or credential variables.

Ownership preflight verifies the database header, canonical schema fingerprint and file-bound marker before SQLite opens or a workspace lock is created. Once exclusively locked, saved schema/state is validated through a read-only handle before writable open. Windows volume binding uses the fixed local CIM volume serial, not the Node-dependent `stat.dev`; same-file reopening was exercised in both directions between official Node 22.13 and the local Node 27 alpha runtime. This is a compatibility regression check, not an alpha-runtime recommendation. WAL header/frame salts and checksum chains are verified in both checksum byte orders; corrupt or incomplete WALs, rollback journals and hardlinked SQLite files are preserved and refused. Recycled trailing WAL frames deliberately fail closed even when they might be inactive: preserve the files for expert recovery or use a verified clean snapshot, rather than deleting sidecars to force startup.

Markerless recreation state and prerelease markers with runtime-specific Windows device numbers require explicit owner-confirmed adoption into another empty private directory; there is no automatic migration. SQLite adoption requires immutable, read-only Python inspection and refuses all sidecars. It preserves the source and saved records, pauses the destination, clears source/output/demo/schedule approvals, interrupts queued/running work and marks uncopied document/backup/recovery files unavailable. Copied databases likewise require explicit adoption or verified snapshot recovery that creates a fresh file-bound marker. Neither a marker nor a profile field proves human identity or protects against intentional same-user tampering.

Output defaults off; approval is rechecked by the worker, including queued jobs after revocation. Common OneDrive/SharePoint/Dropbox/Google Drive/iCloud/Box/Nextcloud/Syncthing roots, configured custom roots, network/removable/unverifiable volumes, and junction escapes are blocked. Unknown synchronization software cannot be universally detected; explicit owner attestation remains necessary. No fallback uploads or arbitrary destination paths are accepted.

Backups include consistent workspace state and only recorded UUID-named generated Markdown files whose current byte length/SHA-256 match their generation records. They are not complete filesystem/source backups or live-source checkpoints. Missing files, older records without hashes and already-unavailable files are explicitly listed as unavailable; unknown files, redirects, hardlinks or changed recorded bytes refuse the backup instead of being silently copied. Bounds are 1,000 document records, 1 MiB per file, 16 MiB combined document bytes, a 256 MiB SQLite snapshot and a 1 MiB manifest. Output approval and private-storage checks remain required; source coverage stays partial even when every eligible document is included.

Recovery verifies the snapshot, ledger-bound manifest and every included document's hash/length before preparing a separate generated workspace. Its file-bound marker is freshly created; schedules/output/demo approvals and source consent are cleared, work is paused, and queued/running jobs are interrupted with matching event/update timestamps. Only verified included files become available after copying; exclusions remain visibly unavailable. Earlier state-only snapshots with a supported owned-database format can recover state but not document contents; markerless snapshots still need explicit adoption. Existing workspaces, backups and unrelated files are not overwritten or pruned; failed partial destinations are preserved for review. Hashes detect corruption, not malicious tampering by a same-user actor able to alter both artifacts and ledger. Either host can explicitly select the recovered directory through its launching environment after the current owner quits; no graphical selector or automatic migration/attachment is added.

Output/demo approval ordering uses the latest successfully applied decision, not merely the latest arriving request: failed grants cannot cancel a pending revocation. Current approvals are checked adjacent to synchronous directory and exclusive file creation, without yielding between check and creation. Backup/recovery additionally rechecks before SQLite setup, owner/lock file creation and later restored-file/state updates. Revocation blocks subsequent operations; a file write or SQLite operation already started, including closing/checkpointing a partial recovery, may finish. Partial artifacts are retained rather than deleted, and recovery preparation clears approvals and pauses work before opening the recovered workspace. These are application event-loop boundaries, not protection against same-user malicious filesystem changes.

One intermediate packaging test omitted explicit data/home/port isolation and reached the recreation's default directory before an occupied-port failure. Filesystem metadata indicated directory/database creation at that attempt's time; prior history cannot be independently established. Contents were not inspected or removed. The reference default is different, but no absolute no-writes claim is made for every possible custom configuration. The backend now reserves its port before creating/opening/recovering state; disposable tests verify byte-identical existing SQLite and no fresh directory after `EADDRINUSE`. Later failures release the listener/lock. Packaging tests use explicit disposable home/data, port zero and a sanitized subprocess environment.
